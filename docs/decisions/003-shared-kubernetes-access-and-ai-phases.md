# 003: Общий Kubernetes-доступ и фазы Plan / Action

Дата: 2026-10-30. Статус: **принято как целевая архитектура; реализация запланирована**.
Владелец: сопровождающие Kubiki desktop/core и AI-домена.
Уточняет [ADR-002](002-integrated-ai-agent.md) в части доступа к Kubernetes,
режимов исполнения и порядка дальнейшей разработки. Остальные решения сохраняются.

## Контекст

Пользователь требует одно подключение для UI и агента, отдельный логический
AI-домен без собственного Kubernetes-ядра, две фазы Plan / Action и приоритет
диагностики. Создание и развёртывание приложений перенесены в конец roadmap.

Сейчас `ai_create_session` получает `Client` из существующего `ClusterClientPool`,
зарегистрированного в Tauri. Следовательно, отдельного AI-пула уже нет. Однако
`agent_tools.rs` напрямую использует `kube::Api` и `Discovery` для части чтений,
а сессия хранит cloned client. Совпадения пула недостаточно для единого контракта
операций, повторной авторизации и обработки смены подключения.

## Решение

Сохранить модульный монолит: React/TypeScript + Tauri/Rust, `kubiki-core` как
владелец Kubernetes-операций, `kubiki-ai` как владелец provider loop и диалога.
В существующем desktop application layer ввести общий `KubernetesAccess` над core.
UI-команды и AI-адаптер вызывают его; создать второе K8s ядро или отдельный сервер
для AI не допускается.

1. Конфигурация, TLS/auth, discovery и connection lifecycle принадлежат общему
   core и `ClusterClientPool`. AI не получает отдельные credentials/kubeconfig.
2. Native backend формирует principal, window/session, scope, connection generation,
   policy revision и execution phase. Полномочия из текста модели не принимаются.
3. Agent policy дополнительно ограничивает доступ текущего подключения. Результат
   проходит field projection до передачи runtime/модели; запрещённые bodies не
   загружаются ради фильтрации, metadata-only использует metadata API.
4. Общие read/diagnostic контракты задают pagination, timestamps, completeness,
   ошибки, deadlines и cancellation. Agent adapter не содержит `kube::Api`,
   discovery или собственного HTTP transport к Kubernetes.
5. При смене context, kubeconfig или поколения подключения agent run
   приостанавливается/отменяется. Повторная привязка явная. Старый сохранённый
   `Client` не является основанием продолжать операции после инвалидирования.
6. Фазы `plan | action` независимы от режимов `read_only | ask | accept`.
   Новая/восстановленная сессия: Read only + Plan. Read only допускает только Plan;
   Ask и Accept допускают обе фазы, начиная с Plan.
7. В Plan нет изменений даже при Accept. Backend ограничивает tool catalog и
   проверяет фазу повторно перед dispatch. Action сам по себе не подтверждает
   конкретную операцию в Ask и не отменяет scope/allowlist в Accept.
8. PlanArtifact хранит Markdown и типизированные identity/version/evidence.
   UI показывает отдельную карточку; Markdown не является исполняемым контрактом
   или approval. Статусы исполнения устанавливает host по receipts.

## Рассмотренные варианты

| Вариант | Преимущество | Решение |
| --- | --- | --- |
| Только общий пул, отдельные AI-операции | Минимум перемещений текущего кода | Недостаточно: остаются дубли discovery/read contracts и lifecycle |
| Общий application service над существующим core | Одна точка доступа и повторное использование без нового runtime | Выбран |
| Отдельный AI Kubernetes backend/MCP с собственными клиентами | Независимое развёртывание | Нет подтверждённой потребности; нарушает требование общего подключения и усложняет отзыв полномочий |

MCP как дополнительный адаптер в будущем возможен лишь поверх того же сервиса
и политики, если появится реальная необходимость. Он не является предпосылкой
для текущей диагностики или локальных моделей.

## Последствия, проверка и миграция

Из `agent_tools.rs` по семействам переносить общие операции в core reads/diagnostics;
подключать UI и AI к одному сервису с контрактными тестами. Существующие
`PreparedMutation` и native mutation guard остаются общими. Не делать двойной
dispatch при миграции; устаревший путь не оставлять обходным fallback.

Основные риски: регрессия общего подключения, устаревший handle, передача в модель
нефильтрованного UI-кэша, обход Plan через tool/approval race и конкуренция за API.
Проверки: cold-start TLS/auth, reconnect, policy/phase revocation, cancellation,
metadata-only transport, нагрузка на UI и диагностика с неполными правами.

Сначала измерить baseline, затем требовать ноль мутаций в Plan, ноль обходов
прав и отсутствие регрессии UI/подключения в том же окружении. Общий сервис
увеличивает область влияния ошибки, поэтому его миграция предшествует расширению
инструментов и требует core review. Ошибки provider изолированы в AI run.

Репозиторий и единица deployment остаются прежними; отдельные AI service, worker
fleet, vector DB и orchestration runtime не вводятся. Сопровождение и incident
ownership остаются у desktop/core; отключение новой AI-фичи не затрагивает ручной
доступ пользователя. Изменения кластера не откатываются отключением функции.
