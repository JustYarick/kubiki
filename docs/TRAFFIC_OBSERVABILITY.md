# Исследование вкладки Traffic

Проверено 30 октября 2026 года. Это предложение реализации; новая вкладка и провайдеры трафика пока не реализованы.

## Нужен ли отдельный сервис

Собственный агент Kubiki не обязателен. Нужен источник наблюдений в кластере: CNI с flow API, service mesh с метриками, eBPF-агент или уже инструментированные приложения. Если такого источника нет, desktop-приложение не может восстановить реальные соединения между Pod только из списка Kubernetes-объектов. Существующая топология Kubiki показывает объявленные связи ресурсов; это не измеренный трафик.

Radar тоже не требует обязательной установки собственного сервиса: он обнаруживает Hubble, Istio, Caretta и Beyla и использует доступный источник. При отсутствии источника предлагает его установку. Hubble читается через Relay; остальные источники — через Prometheus-совместимый backend. Это подтверждается [документацией Radar](https://radarhq.io/docs/features/traffic).

## Варианты интеграции

| Что уже есть | Что использовать | Что получим | Чего может не хватать |
| --- | --- | --- | --- |
| Cilium + Hubble Relay | Hubble Observer gRPC API через Rust | Направление соединений, Pod/namespace, порты, протоколы, verdict/drop reason; L7 при соответствующей настройке | Включённых Hubble/Relay, маршрута и TLS-настроек. Сам факт наличия Cilium не гарантирует доступный API |
| Istio + сбор метрик | Prometheus HTTP API | Граф запросов, RPS, HTTP/gRPC ошибки, гистограммы задержек; TCP-соединения и объём данных | Рабочего scrape и подходящих labels. Наличие istiod само по себе не даёт историю запросов |
| Calico с flow logs | Goldmane gRPC API | Наблюдаемые сетевые потоки и решения политик | Совместимого способа установки и включённого Goldmane. Whisker — отдельный UI, Kubiki он не нужен |
| Caretta | Prometheus/VictoriaMetrics | Связи TCP между workload на основе eBPF | Рабочих агентов на нужных узлах, flow-метрик и scrape. HTTP-коды и задержки запросов не следует обещать |
| Beyla / Alloy с Beyla | Prometheus HTTP API | Сетевые связи; поддерживаемая инструментация также даёт HTTP RED-метрики | Включённого сбора network-метрик и нужных атрибутов. Настройки и имена метрик зависят от версии |
| Обычный CNI без телеметрии | Пока только объявленная топология | Service selectors, EndpointSlice, маршруты, NetworkPolicy | Источника реальных потоков; для этого понадобится установка/включение сбора |

Основания для таблицы: [Hubble setup](https://docs.cilium.io/en/stable/observability/hubble/setup/), [стандартные метрики Istio](https://istio.io/latest/docs/reference/config/metrics/), [Goldmane и Whisker](https://docs.tigera.io/calico/latest/observability/enable-whisker), [Caretta](https://github.com/groundcover-com/caretta), [Beyla](https://grafana.com/docs/beyla/latest/), [экспорт метрик Beyla](https://grafana.com/docs/beyla/latest/configure/export-data/).

Calico: Goldmane может работать независимо от Whisker; документация отмечает ограничения способа установки и статус tech preview. Нельзя определять доступность API только по имени CNI.

Istio ambient: ztunnel даёт L4-наблюдения, а L7-возможности требуют waypoint на соответствующем пути. Следует учитывать reporter и не суммировать повторно наблюдения разных прокси. Источники: [ambient observability](https://istio.io/latest/docs/ambient/usage/troubleshoot-ztunnel/), [waypoint](https://istio.io/latest/docs/ambient/usage/waypoint/).

Hubble: L7 proxy/rules — дополнительная настройка. L7 NetworkPolicy одновременно влияет на разрешённый трафик, поэтому включать такие политики автоматически ради визуализации нельзя. L3/L4-наблюдение не расшифровывает содержимое HTTPS. Источник: [L7 visibility](https://docs.cilium.io/en/stable/observability/visibility/).

## Что доступно в локальном testbed

Проверены только чтения Kubernetes API с явным `--context testbed`; ничего не устанавливалось и не менялось.

- Есть DaemonSet `caretta/caretta`, образ `quay.io/groundcover/caretta:v0.0.16`.
- Есть Service `caretta/caretta-vm`, HTTP-порт `8428`, и `caretta-grafana`.
- Prometheus-совместимый endpoint `/api/v1/label/__name__/values` доступен через Kubernetes Service proxy и возвращает `status: success`.
- Обнаружены служебные метрики Caretta, включая `caretta_ebpf_connections_map_size`. В списке имён не обнаружены метрики со словом `link`. Это подтверждает доступность backend, но пока **не подтверждает наличие пригодных flow-данных**. До реализации адаптера надо проверить работу eBPF-проб и фактический набор экспортируемых метрик этой версии.

Это хороший кандидат для первого локального прототипа без установки ещё одного агента. Наличие источников в остальных кластерах не проверялось.

## Предлагаемая реализация в Kubiki

Рекомендации ниже — вывод исследования и проектное предложение.

1. Отдельная вкладка Traffic с переключателем источника и явным состоянием подключения. Сначала обнаружение, затем проверка доступности API и данных. Отсутствие разрешения, источник без данных и нулевой трафик показываются как разные состояния.
2. Подключение из Rust: существующий kubeconfig/context, Service proxy для HTTP либо port-forward для gRPC. Для Hubble/Goldmane учитывать собственную аутентификацию и TLS: kubeconfig сам по себе её не заменяет. Внутренние endpoints не требуется публиковать наружу.
3. Единый контракт провайдера: источник, namespace, окно времени, timestamp, source/destination Pod/workload, протокол, порт, наблюдаемое количество/единица измерения, опциональные ошибки, latency, verdict и сведения о неполном покрытии.
4. Возможности UI определяет провайдер: TCP connections/bytes не называем HTTP RPS; p95 не вычисляем без подходящей гистограммы; индивидуальные flow-записи не выдумываем из агрегированных Prometheus-счётчиков. Время хранения зависит от источника: live-буфер не равен историческому хранилищу.
5. Сначала таблица связей и ограниченный граф на существующих React Flow/ELK. Фильтрация по namespace, времени и выбранному workload, раскрытие в Pod, переход в существующие Details. Не смешивать несколько источников в один счётчик.
6. Для больших кластеров: фильтрация до передачи в React, ограниченные очереди и число рёбер, backpressure, отметка усечения/потери событий, отмена чтений при смене context. Наблюдаемые потоки не означают наличие всех потоков.
7. При отсутствии источника — конкретное объяснение и варианты настройки. Автоустановка CNI/mesh или привилегированного агента в эту функцию не входит.

Порядок работ: проверить реальные flow-метрики уже установленной Caretta; реализовать общий Prometheus-адаптер с отдельными схемами Caretta/Istio; затем Hubble gRPC; после этого Goldmane и Beyla. Если приоритетный кластер уже использует Hubble, начать с него. Установка Istio или замена CNI только ради графика не требуется.
